I've created an STM32 project based on the STM32H523CET6. This code is going to listen for messages coming in over a UART and needs to be able to send messages out the same way. It will also have a bunch of other functions, however, so the UART communication needs to be, as far as possible, non-blocking.

I have the UART configured on pins PA9 and PA10. The device at the other end will be an ESP32-S3 module. The wire length between the two boards will be no more than 15cm. So I'd like the fastest reliable serial speed.

I'm coding in VS Code using the STM32 official extensions, having made the initial configuration via STM32CubeMX.

Can you write functions and any necessary main loop code to respond to incoming messages. These will be commands within a defined set, so we'll need a function with a switch statement to parse the commands. Some commands will be simple ('START', 'STOP') and others will have parameters. I've decided on a message protocol where any parameters always follow a command separated by colons - eg, 'SPEED:30' or 'TURN:L:15'.

We'll also need a function for sending messages using the same protocol.

The inputs with interrupts (PB0-PB2, PB4-PB8) are data lines for my own bit-banged serial protocol. I'll also need functions to deal with the following:

- When one of those lines goes low, it triggers an interrupt. The ISR needs to look at which line is low (it will select the first line it finds to be low) and sets a flag accordingly. We're dealing with 'DAT' lines 0-7, so the flag should be an int (perhaps uint8_t) that is set to 0-7, but is 255 otherwise.
- The main loop should poll this flag, if set to values 0-7 it calls a function which will handle the communication.

Because of this use of interrupts, we're going to need to decide when interrupts get disabled & re-enabled. For instance, do they need to be disabled during UART communications? When the main loop responds to an interrupt flag, we probably need to disable further interrupts during the resulting bit-banged communication.

The bit-banged comms will be short, simple messages, probably no more than, say, 15 bytes, although they will vary in length. Some could be as short as a single byte.

I'm assuming that using the HAL is fine for this kind of application, but if there are compelling reasons to go bare metal then I'm fine with that too.
